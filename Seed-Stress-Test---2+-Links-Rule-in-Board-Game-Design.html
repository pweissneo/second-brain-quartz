Seed Stress Test: 2+ Links Rule in Board Game Design

Tested Rule: Every note must link to at least 2 other notes OR be tagged with foundational: true OR be tagged with specialized: true.

Test Domain: Board Game Design Knowledge Base

Does the Rule Make Sense for Board Game Design?

Yes, with significant nuances. Board game design is a creative-experiential hybrid domain with unique characteristics:

  • Game mechanics are highly interconnected (mechanics combine, conflict, and enhance each other)
  • Design phases create temporal dependencies (ideation → prototyping → testing → refinement)
  • Target audience and player count create context-specific knowledge
  • Theme and mechanics have complex relationships
  • Component knowledge intersects with manufacturing and cost considerations

However, board game design also contains categories that challenge the 2-link minimum in ways not fully addressed by existing edge cases.

Is the Test Executable?

Yes — Counting outgoing links is straightforward. However, board game design reveals several edge cases where:

  • The note has genuinely meaningful connections (passing intent)
  • But has fewer than 2 outgoing links (failing the letter of the rule)
  • Or has exactly 2 links that are both categorical/hierarchical (technically passing but arguably decorative)

Edge Cases Discovered

1. Core Game Components (Physical)

Problem: Notes about fundamental game components (“Six-Sided Die,” “Playing Card,” “Game Board,” “Token”) might only link to:

  • Random Generation (for dice/cards)
  • Component Types

That’s only 2 links. Are both meaningful connections, or is this decorative?

Analysis: These are physical primitives in board games - equivalent to “salt/oil” in cooking or “major scale” in music. They serve as category anchors rather than conceptual bridges.

Current Edge Case Coverage: The existing “specialized: true” edge case covers “domain-specific instruments, tools, or assessment scales.” Game components are arguably instruments (you “use” dice to generate randomness) but they’re more fundamental than instruments.

Recommendation: Add explicit category for physical primitives:

Edge case: Core game components (dice, cards, boards, tokens) are physical primitives that anchor component categorization. Tag with component-type: primitive rather than specialized: true to distinguish from tools/instruments.

2. Game Mechanic Primitives

Problem: Notes about fundamental mechanics (“Dice Rolling,” “Card Drawing,” “Resource Tracking,” “Turn Order”) face similar challenges:

  • “Dice Rolling” → links to Random Generation, Dice Mechanics
  • That’s 2 links, both category relationships

Deeper Issue: These are MECHANIC primitives, not physical components. The distinction matters:

  • Physical components: what the game is made OF
  • Mechanical primitives: what players DO in the game

Recommendation: Add mechanic-type: primitive for fundamental player actions:

Edge case: Core mechanic primitives (dice rolling, card drawing, resource tracking, turn order) represent fundamental player actions. Tag with mechanic-type: primitive alongside foundational: true when appropriate.

3. Design Phase Notes (Temporal)

Problem: Notes about design phases (“Ideation,” “Prototyping,” “Playtesting,” “Final Polish”) might only link to:

  • “Ideation” → links to Design Process, Brainstorming
  • That’s 2 links, both pointing backward or forward in time

Analysis: Design phases are sequential - they naturally form a chain, not a web. Forcing 2+ outgoing links creates artificial cross-connections.

Current Edge Case Coverage: The Seed mentions “sequential knowledge (history, processes, narratives)” has homogeneous cause/effect links and acknowledges this exception. But design phases aren’t exactly “sequential knowledge” in the historical sense - they’re workflow stages.

Recommendation: Clarify workflow/phase knowledge:

Edge case: Notes representing workflow phases (design stages, process steps, project milestones) may have fewer natural links because they connect primarily to adjacent phases. Use workflow-phase: true frontmatter to mark these notes for link-threshold relaxation.

4. Genre/Category Hub Notes

Problem: Notes like “Worker Placement,” “Deck Building,” “Tile Placement” - these are mechanic categories:

  • “Worker Placement” → links to Game Mechanics, Resource Management
  • That’s 2 links, both hierarchical (genre → specific)

Analysis: Genre hub notes are categorization tools, not conceptual bridges. They help users FIND notes, not UNDERSTAND concepts.

Comparison: This is similar to hub notes in other domains but with a twist: game design genres overlap (a game can be “deck building” AND “worker placement”). Single-genre notes might not capture this.

Recommendation: Genre notes should use multi-genre tagging:

Edge case: Game genre/mechanic category notes may have fewer conceptual links because they serve as FILTERING tools rather than conceptual bridges. Add category-type: genre-filter to distinguish from conceptual hubs.

5. Specific Game Examples

Problem: Notes about specific published games (“Catan,” “Terraforming Mars,” “Wingspan”) might only link to:

  • “Catan” → links to Settlers of Catan, Gateway Games
  • But wait - “Settlers of Catan” IS the note, so that’s self-referential or weak

Deeper Issue: A note about a specific game might link to:

  1. Its designer(s)
  2. Its primary mechanic(s)
  3. Its target audience

That’s 3 links - technically passing. But if the vault is small, these links might not exist.

Analysis: Specific game notes are case studies, not concepts. They should LINK FROM others, not TO others necessarily.

Current Edge Case Coverage: The Seed has “universal/primitive elements…may legitimately have zero backlinks” edge case. But this is about backlinks (incoming), not outgoing links.

Recommendation: Add case-study notes guidance:

Edge case: Notes about specific instances (individual games, specific designs, concrete examples) may have fewer outgoing links because they are referenced BY conceptual notes, not the reverse. These should track backlinks rather than outgoing links.

6. Component Specification Notes

Problem: Notes about component specifications (“Poker-Size Cards,” “Standard Dice Size,” “Box Dimensions”) might only link to:

  • “Poker-Size Cards” → links to Card Sizes, Component Standards
  • That’s 2 links, both reference/hierarchical

Analysis: These are lookup/reference notes, like dictionary definitions. The user looks UP this information, doesn’t EXPLORE from it.

Current Edge Case Coverage: The Seed’s “standard terminology” edge case covers abbreviations and domain vocabulary. Component specifications are technical standards, not terminology.

Recommendation: Extend reference-note handling:

Edge case: Component specification and technical standard notes (sizes, materials, tolerances) may have fewer outgoing links because they serve as REFERENCE lookups. Tag with type: specification to distinguish from conceptual notes.

7. Legacy/Vintage Game Notes

Problem: Notes about older games (“Risk,” “Monopoly,” “Twilight Struggle”) might have fewer connections in a modern-focused vault:

  • Old games → might only link to Game History, Classic Games
  • Limited contemporary references if the vault focuses on modern designs

Analysis: This is similar to the “trend-specific” knowledge in fashion - temporal bounding affects connectivity.

Current Edge Case Coverage: There’s no explicit temporal bounding edge case for outgoing links.

Recommendation: Add temporal scope to link context:

Edge case: Notes about historical/legacy games may have fewer contemporary links because the knowledge is temporally bounded. Use temporal-scope: legacy frontmatter to mark these notes.

8. Player Count / Play Time Specifications

Problem: Notes about player count ranges (“2-4 Players,” “4-6 Players”) or play time categories (“30 min,” “60 min,” “120+ min”) might only link to:

  • “2-4 Players” → links to Player Count, Game Length
  • That’s 2 links, both specification-like

Analysis: These are PARAMETER notes, not conceptual notes. They’re used to FILTER games, not to learn from.

Recommendation: Add parameter-note handling:

Edge case: Game parameter notes (player count, play time, age range) serve as filter criteria, not conceptual content. Tag with type: parameter and allow fewer outgoing links.

9. Theme vs Mechanics Tension

Problem: Notes exploring theme-mechanics relationship (“Thematic Integration,” “Ameritrash vs Eurogame”) might only link to:

  • “Thematic Integration” → links to Theme, Mechanics
  • That’s 2 links, but the relationship itself is the content

Analysis: These are comparative/relational notes. The VALUE is in the relationship, not in the topics themselves.

Current Edge Case Coverage: There’s a comparative notes edge case (“single comparative note for binary choices where comparison IS the insight”).

Recommendation: Ensure relational notes are covered:

Edge case: Relational/comparative notes where the relationship IS the knowledge (theme-mechanics, luck-skill balance, competition-cooperation) may have exactly 2 links (the two things being related) but represent meaningful knowledge.

10. Design Pattern Notes (Emerging)

Problem: Notes capturing design patterns (“Engine Building Pattern,” “Tableau Building,” “Action Queue”) might only link to:

  • “Engine Building” → links to Game Mechanics, Resource Management
  • That’s 2 links, both categorical

Analysis: Design patterns in games are emerging concepts - they’re not universally defined like genres. A note about “Engine Building” might be:

  1. Defining what it IS (mechanic definition)
  2. Listing examples (case studies)
  3. Discussing design considerations (principles)

If it only does #1, it has few natural links.

Recommendation: Pattern notes should specify scope:

Edge case: Game design pattern notes should specify their scope (definition-only vs examples-included vs principles-discussed) to help assess appropriate link thresholds.

Refinements Needed

Refinement 1: Add Physical/Material Primitives Category

Proposed addition:

Edge case: Core physical components (game pieces, cards, boards, dice) serve as material primitives that anchor component categorization. Tag with component-type: primitive to distinguish from tools/instruments and apply relaxed link thresholds.

Refinement 2: Add Mechanic Primitives Category

Proposed addition:

Edge case: Core player action primitives (dice rolling, card drawing, resource tracking, turn order) represent fundamental game mechanics. Tag with mechanic-type: primitive alongside foundational: true.

Refinement 3: Clarify Workflow/Phase Notes

Proposed addition:

Edge case: Workflow phase notes (design stages, development milestones, testing phases) may have fewer natural links because they connect primarily to adjacent phases in sequence. Use workflow-phase: true to mark these notes for threshold relaxation.

Refinement 4: Distinguish Filter/Category Notes

Proposed addition:

Edge case: Notes serving primarily as filters (genre categories, player count specs, play time specs) rather than conceptual content may have fewer outgoing links because users navigate TO these notes for filtering, not FROM them for learning.

Refinement 5: Add Case Study Note Type

Proposed addition:

Edge case: Notes about specific instances (individual games, specific projects, concrete examples) may have fewer outgoing links because they are referenced BY conceptual notes, not vice versa. Track backlinks rather than outgoing links for these notes.

Board Game Design-Specific Test Summary

For board game design knowledge bases:

  • Physical components (dice, cards, boards): Use component-type: primitive
  • Mechanical primitives (rolling, drawing, tracking): Use mechanic-type: primitive
  • Design phases (ideation, prototyping, testing): Use workflow-phase: true
  • Genre categories (worker placement, deck building): Use category-type: genre-filter
  • Specific games (case studies): Track backlinks, not outgoing links
  • Component specs (sizes, standards): Use type: specification
  • Legacy games: Use temporal-scope: legacy
  • Parameter notes (player count, time): Use type: parameter
  • Relational notes (theme-mechanics): Existing comparative note rules apply
  • Design patterns: Specify scope (definition/examples/principles)

Conclusion

The 2+ links rule works for board game design with new categories. The domain’s unique combination of:

  • Physical components (material primitives)
  • Player actions (mechanic primitives)
  • Design workflows (phase notes)
  • Categorization needs (genre filters)
  • Instance-based knowledge (specific games)

…requires explicit edge cases. The proposed refinements would make the rule more executable in board game design while preserving its intent (meaningful connectivity).
