Seed Gap - Vault Integrity and Disaster Recovery

The Problem

The Seed covers individual note lifecycle management and version control guidance for knowledge with dependencies. But it completely lacks rules for:

  1. Vault-level backup strategies — how should an AI agent set up automated backups?
  2. Disaster recovery procedures — if the vault is corrupted or lost, how does the AI know how to restore it?
  3. Integrity verification — how does the AI periodically check that the vault hasn’t developed silent corruption (broken links, orphaned nodes, data drift)?
  4. Migration strategies — moving between storage backends, tools, or hosting platforms

Without these rules, an AI agent building a knowledge base has no guidance on protecting the user’s accumulated work.

Why This Matters

Knowledge bases grow in value over time. A vault with 500+ notes represents hundreds of hours of curation, verification, and synthesis. Losing that work would be catastrophic. The Seed invests heavily in content quality but ignores asset protection.

Proposed Rule

Rule: Implement vault-level integrity and recovery infrastructure — automated backups, periodic integrity verification, and documented recovery procedures.

Why: Knowledge bases accumulate irreplaceable work over time. Content quality rules without protection rules mean accumulated knowledge is vulnerable to loss from hardware failure, corruption, or migration errors. Protection is a prerequisite for long-term vault value.

Test (executable by AI agent):

  1. Can you find a vault-backup-config.yaml or equivalent in the vault root directory?
  2. Does it specify backup location(s), frequency, and retention policy?
  3. Has a backup been performed in the last 7 days?
  4. Can you find a vault-recovery-procedure.md document?
  5. Does the vault run automated integrity checks (broken links, orphaned nodes)?
  6. Is there a vault-migration-checklist.md for tool/backend transitions?

If any test fails: Create the missing artifact and add backup/integrity tasks to the vault’s operational routine.

Implementation

Vault Configuration File

Recovery Procedure Document

  1. Run integrity checks

    • Validate all frontmatter schemas
    • Check graph connectivity
    • Verify Seed rule compliance

  2. Validate content

    • Spot-check recent notes for completeness
    • Verify no data loss beyond expected rollback

Selective Note Recovery

  1. Find note in git history: git log --all --full-history -- <note-name>.md
  2. Recover from specific commit: git show <commit-hash>:<note-name>.md > <note-name>.md
  3. Validate recovered note’s links and metadata

Migration Checklist

When moving vaults between tools/platforms:

  • Export all notes in portable format (Markdown)
  • Verify export completeness (note count, file sizes)
  • Validate wikilink syntax for target platform
  • Test frontmatter compatibility
  • Run integrity check on migrated vault
  • Verify graph connectivity preserved
  • Update all internal references to reflect new location

### Integrity Check Implementation

```bash
#!/bin/bash
# vault-integrity-check.sh — run weekly

VAULT_DIR=~/workspace/ai-assisted-knowledge-management-vault

# Check for orphaned nodes
orphaned=$(find "$VAULT_DIR" -name "*.md" -not -name "_root.md" -not -name "CLAUDE.md" | while read f; do
  links=$(grep -oE '\[\[[^]]+\]\]' "$f" | wc -l)
  backlinks=$(grep -l "$f" "$VAULT_DIR"/*.md 2>/dev/null | wc -l)
  if [ "$links" -eq 0 ] && [ "$backlinks" -eq 0 ]; then echo "$f"; fi
done | wc -l)

# Check for broken wikilinks
broken=$(grep -rE '\[\[[^]]+\]\]' "$VAULT_DIR"/*.md | while read line; do
  target=$(echo "$line" | sed -E 's/.*\[\[([^\]|]+).*/\1/')
  if [ ! -f "$VAULT_DIR/$target.md" ] && [ ! -f "$VAULT_DIR/${target#*/}.md" ]; then
    echo "$line"
  fi
done | wc -l)

# Report
echo "Orphaned notes: $orphaned"
echo "Broken links: $broken"

Edge Cases

  1. Very small vaults (<10 notes): Full backup infrastructure may be overkill. Apply simplified rules — weekly backup + monthly integrity check sufficient.

  2. Git-based vaults: Backup is inherent (git push to remote). Focus on verifying remote push is working and test restore from another clone.

  3. Multi-vault systems: Each vault needs its own backup config. Additionally, need cross-vault reference integrity (links between vaults).

  4. AI-managed vaults: AI agents may not have access to system-level backup tools. Use git-based backup and cloud storage APIs. Document what the AI can and cannot automate.

  5. Cryptographic integrity: For high-value vaults, consider storing SHA256 hash of vault state and verifying against hash before restoration.

  6. Incremental vs full backup: Large vaults (>1000 notes) should use incremental backup to avoid storage bloat. Track incremental backup chain integrity.

  7. Backup corruption: Backups can themselves become corrupted. The “verify backup” step is critical — don’t assume backups work without testing.

  8. Migration with link rewriting: When migrating between platforms, wikilink syntax may change. Automated link rewriting must be tested against a sample before full migration.
